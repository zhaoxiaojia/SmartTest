## 1. 已确认需求

1. 内网 PC 上的 Web Server 通过脚本自动完成当期审查、汇总、历史保存和邮件发送，用户不需要整理、上传或维护每期结果。
2. 分别发送 Jira 规范审查邮件、Confluence 项目信息更新审查邮件，参考 Coco 提供的截图结构。
3. 每次触发生成新的执行历史；手动触发与定时触发使用同一机制。同一天或同一周多次执行不合并、不覆盖。
4. 邮件最多展示本次及此前三次结果，最新记录在最左侧。不足四次展示实际已有记录。全部历史长期保留，不因展示窗口滚动而删除。
5. 后续固定每周五北京时间 15:00 触发一次。统计机制不依赖触发频率，也不按自然周作为记录唯一键。
6. Web 提供管理入口，调试阶段有“立即触发”按钮；业务确认后移除该按钮，保留定时功能。
7. 使用 Coco 指定的 `aut-faq-qa` 发件邮箱；调试收件人为 `chao.li` 和 `ping.xiong`。准确完整地址见第 9 节。
8. 保留内网可复制、搬运分析的运行打印。此项属于正式需求，交付清理时不得作为临时调试残留删除。

## 3. 拟议后台设计

### 3.1 同一个执行入口

```text
固定周五 15:00 调度 / Web“立即触发”
  → 创建执行记录（run_id、触发来源、时间、配置快照）
  → 使用已配置后台身份，建立数据库审查范围快照
  → 调用现有 Jira / Confluence 审查与导出 owner
  → 保存两类当期明细和汇总
  → 分别读取当前结果及此前最多三次可用结果
  → 渲染两封 HTML 邮件，附上当期 XLSX
  → 分别发送并记录 SMTP 结果、失败阶段和耗时
```

拟新增的编排接口为 `trigger(source: Literal['manual', 'scheduled']) -> run_id`。手动 API 立即返回执行 ID，页面查询状态；请求不等待整段审查和 SMTP 完成。调度器只调用该入口，不拥有另一套审查或统计逻辑。

每次执行冻结自己的筛选条件、时间窗口和实际数据库快照引用。后台身份和持久配置不依赖某个仍在线的浏览器；服务端按身份授权范围创建本次查询快照，后续审查/导出只消费它。未配置范围不能静默回退到全量数据。

### 3.2 SQLite 持久记录

拟在现有 WebDatabase 上新增独立业务表，不复用远端对象版本历史，也不加入可废弃缓存重建范围：

| 表 | 主要内容 |
| --- | --- |
| `audit_email_settings` | 启停、收件配置、审查条件、后台身份引用；频率固定，不提供 cron 编辑器 |
| `audit_email_runs` | 执行 ID、触发来源、创建/结束时间、执行状态、配置和范围快照引用 |
| `audit_email_results` | 执行 ID、报告类型、统计口径版本、审查窗口、汇总、当期明细、渲染正文和附件信息 |
| `audit_email_deliveries` | 执行 ID、邮件类型、收件人、发送状态、时间、可诊断错误 |

上述职责允许在实现时合理合表，但不得丢失逐次记录、两封独立状态和历史持久性。附件文件放在内网服务器持久目录，SQLite 保存归属与路径；不依赖登录会话结束就清理的临时下载目录。凭据接入现有安全配置/凭据 owner，不将明文密码放入页面 payload 或历史快照。

同周重复执行允许多条记录；邮件列按执行先后排序，以 `run_id` 区分。同日多次执行时显示时间，历史截图仅有日期的记录保留原日期标签，不编造具体时刻。

### 3.3 错误及生命周期处理建议

以下是本次设计建议，随本文一起审阅，不视为已确认业务规则：

- 一封邮件失败不掩盖另一封的结果；两类结果和发送状态独立记录。
- 失败执行仍保留历史，但未生成完整统计的结果不伪装成零值或通过结果。该类型邮件的对比从实际成功生成的汇总中取最近四次，发送失败不删除已完成汇总。
- 不自动重发、不自动补跑停机错过的周期。再次手动触发是新执行记录。
- Web Server 启停时注册/关闭调度器；当前方案以单个负责调度的 Web 进程部署，不允许每个 worker 各自发送。部署形态如需多 worker，实施前明确唯一调度 owner。
- 执行中的并发触发策略需在实现前核对现有任务机制，避免为了防重复把同周记录合并；任何新增拒绝/排队规则须报告 Coco。

## 5. 两封邮件的拟议格式

### Jira

- 主题：`FAE QA JIRA描写不符合规范反馈 {当期日期}`。
- 开头：`Hi all,` 加本次实际审查日期范围及客观结果说明。
- 对比表：生成时间、问题总数、通过 Jira 数、不通过 Jira 数、通过率；最多四列记录，当前列黄色强调。
- 当期违规表：创建人、违规 Jira 数量、违规 Jira 号；蓝色表头，编号附原始 Jira 链接。按 Issue 去重计数，不能把违规规则条数当作 Jira 数量。
- 附件：现有 Jira 审查 XLSX，仅附当期数据。

### Confluence

- 主题：`Confluence信息更新检查结果 {当期日期}`。
- 开头：`Hi all,` 加本次实际检查范围和中性提醒。
- 对比表：四条产品线，各期展示“已更新点 / 需要更新点”；最多四列记录，最新在左侧。
- 附件：沿用现有按产品线导出的当期 XLSX；有数据的产品线按现有导出行为生成，不自行补造空附件。
- 分子拟为现有审查结果中 `UPDATED` 的更新点数量；分母的业务含义必须按第 9 节确认，不能仅凭截图比值猜测。

两封邮件均使用 HTML 表格和内联样式，适配公司 Outlook；复用现有 MIME/SMTP，不复制截图中的邮件客户端按钮、个人签名、红字点名或无依据的改善结论。邮件预览复用同一正文渲染结果。

## 8. 验收标准

| 项目 | 通过条件 |
| --- | --- |
| 自动化 | 配置完成后无需用户逐期整理；无人值守生成两类审查汇总、历史和邮件 |
| 执行记录 | 每次触发独立留痕，同周不覆盖；失败也可追查 |
| 对比 | 每封最多四次完整结果，当前在左；种子与新结果可接续 |
| 持久化 | 重启、页面切换和缓存刷新不丢历史；不依赖浏览器 ID 列表 |
| 时间 | 固定北京时间周五 15:00；手动触发不改变后续定时时间 |
| 邮件 | 两封布局符合本设计和截图，明细/统计/附件一致，真实发送给批准的调试地址 |
| 调试 | 能搬运一次执行的完整阶段打印定位失败，不泄漏凭据 |
| 管理 | 有 Settings 入口、定时启停、状态与历史查看；调试按钮在业务确认前可用 |
| 质量 | 复用既有审查/邮件/日志/SQLite owner，无重复机制、无无关变更 |
