# SmartTest 统一 AI 模型与 Jira 审查设计

## 目标

统一整理 `support/ai` 中的模型配置、凭据存储和 LLM 调用接口，并让 Common Tools 的 Jira 审查复用该入口完成“字符规则初审 + AI 模糊边界复核”。

根目录 `jira_handler.py` 仅作为当前业务规则参照，保持独立：SmartTest 不修改、不导入、不依赖该文件。

本设计取代同日仅面向 DeepSeek 环境变量和根目录脚本改造的旧设计。实现范围以本文为准。

## AI 模型边界

### 内置模型模板

首版提供以下固定模板：

1. 公司内网 Kimi。
2. 公网 DeepSeek。

公司内网 DeepSeek 暂不提供。只有取得准确且经过验证的服务地址和模型 ID 后，才通过同一模型注册表增加；不得保留空模板、占位值或猜测配置。

模板由 SmartTest 维护，至少声明：

- 稳定的模板 ID 和界面显示名称；
- 凭据 ID；
- OpenAI-compatible 服务地址；
- 模型 ID；
- 超时、最大输出长度等安全默认值；
- JSON 输出、关闭思考模式等模型特有请求选项。

用户不能修改服务地址和模型 ID，只能选择模板并配置对应 API Key，避免错误配置进入业务代码。

### 统一 LLM 接口

`support/ai` 是 SmartTest 唯一的 AI 调用入口，职责收敛为：

- 模型模板注册与查询；
- 当前模型选择；
- API Key 的安全存取；
- 统一 `chat` 调用；
- OpenAI-compatible 协议适配；
- 统一配置、传输和响应异常。

Kimi 与 DeepSeek 使用同一套 OpenAI-compatible 客户端。只有真实存在的请求差异通过模板选项适配，不为每个模型复制 HTTP、JSON、超时和异常处理代码。

业务模块只传递消息、结构化输出要求和调用参数，不接触 `base_url`、API Key 或底层客户端创建。

### 清理范围

移除或替换以下旧机制：

- 单一 `DEFAULT_AI_MODEL` 和单一 API Key 假设；
- Jira 内部直接创建 OpenAI/DeepSeek 客户端；
- 面向某个模型的重复配置加载入口；
- 可由统一客户端和模型模板覆盖的薄包装；
- 已失效的环境变量专用设计和重复测试。

环境变量仅可作为部署兼容输入，不能成为桌面用户配置的唯一方式。

## API Key 安全设计

API Key 按凭据 ID 使用 Windows DPAPI 加密，密文保存在当前 Windows 用户的 SmartTest 应用数据目录。

- 普通设置只保存当前模型模板 ID，不保存 Key。
- QML 只能查询“已配置/未配置”，Python 不向 QML 返回已保存 Key。
- 用户保存后立即清空密码输入框。
- 日志、异常、Jira 结果和导出文件不得包含 Key。
- 不在源码、QRC、翻译文件、打包配置或安装包中嵌入明文 Key。
- 不同凭据默认相互隔离；需要共享 Key 时由模板显式使用同一凭据 ID。

当前机器已有的旧版 DPAPI 单 Key 存储来自原公司内网 Kimi 配置。升级时将它迁移到公司内网 Kimi 的凭据 ID；公网 DeepSeek 保持未配置。迁移不得产生明文中间文件。

## Settings 界面

Settings 新增“AI 模型配置”区域：

- 当前模型模板下拉选择；
- 当前模板的 API Key 密码输入框；
- “保存”和“清除”操作；
- “已配置/未配置”状态；
- 必要的成功或错误提示。

切换模板只刷新配置状态，不回填已保存 Key。保存或清除只影响当前模板对应的凭据。

Settings 通过专用 Python 桥接调用 `support/ai`，不使用通用字符串设置接口保存秘密。

## Jira 审查流程

Common Tools 的 Jira 审查采用以下阶段：

1. **解析输入**：检查空值，并识别 JQL、Issue URL、Filter URL 或 Search URL。
2. **验证并获取**：使用现有 Jira 登录与传输层验证 JQL，分页获取审查字段。
3. **字符初审**：执行从当前 `jira_handler.py` 对齐的确定性规则。
4. **候选分流**：明确违规直接保留；仅将规则声明允许 AI 复核的模糊项作为候选。
5. **AI 复核**：通过 `support/ai` 当前模型复核候选；同一 Jira 的候选合并为一次请求。
6. **结果合并**：
   - AI 判定 `PASS`：移除对应初审违规；
   - AI 判定 `FAIL`：保留违规并采用 AI 的原因和修改建议；
   - 未配置、超时、请求失败或响应无效：保留字符初审结果，并标明 AI 未完成复核。
7. **结果确认**：展示规则明细、问题列表和各阶段状态，等待用户确认。
8. **导出**：确认后使用现有 `openpyxl` 导出至下载目录，并允许在文件管理器中定位文件。

AI 不新增规范范围之外的规则，也不对明确合规或明确违规项进行复核。没有候选项时不初始化 LLM、不发送请求。

## 状态与进度

前端展示以下稳定阶段：

- 解析输入；
- 获取 Jira；
- 字符审查；
- AI 复核；
- 整理结果；
- 等待确认；
- 导出完成。

进度按已处理 Jira 数量更新。AI 阶段可显示候选 Jira 总数与完成数。单个 AI 请求失败不终止其他 Jira，也不丢失字符初审结果。

## 代码边界与复用

- `support/ai` 拥有所有模型、凭据和 LLM 调用行为。
- `support/jira_integration/audit` 拥有 Jira 审查规则、候选分流、AI 裁决合并和报告模型。
- Jira 传输继续复用现有登录和客户端。
- UI Bridge 只负责线程、状态转换和 QML 数据映射。
- QML 只负责输入、展示、确认和操作。
- 导出继续复用 `openpyxl`，不自行实现 XLSX/XML。

不修改 Redmine 及其他业务逻辑，不复制根目录 `jira_handler.py` 的 CLI、控制台进度、客户端创建或独立导出流程。

## 测试与验收

只保留能保护长期行为的测试：

- 两个内置模型模板可被统一入口解析；
- 当前模型选择持久化；
- 不同凭据的 Key 相互隔离；
- 旧 Kimi Key 可安全迁移；
- QML/Bridge 不回传 Key 明文；
- 字符规则能区分明确违规和 AI 候选；
- 一个 Jira 的多个候选只产生一次 AI 请求；
- AI `PASS`、`FAIL`、缺失配置、异常和无效响应均正确合并或降级；
- 没有候选时不调用 AI；
- Jira 审查阶段和确认后导出流程正确；
- 打包依赖和资源声明包含实际运行所需内容。

交付前删除临时脚本、历史 RED 证据、重复等价用例、源码形状断言、缓存和调试输出。最终要求 scoped tests、语法检查、QML 离屏启动检查和 `git diff --check` 通过。
